# 架空名簿暗号化形式 v1（第5段階）

基準: `f71ce22d3fb023407c69d41ad655ba7fd5092977`。
既存画面・保存領域から独立した実験用モジュール。正式認証・実データ接続・移行・保存・復元を実装しない。

## APIと入力

`FlowerFictionalRosterCrypto.createDemoCrypto(boundary, session, scope)`。
`scope` は親が確定した `{classId, schoolYear, baseYear}`。既存6クラスID、基準年度のサフィックスなし／他年度の `-year-<年度>` を変更しない。
有効な同一クラス・年度の `demo` セッションだけを許可し、各非同期処理の前後にも失効を検査する。

- `encrypt(fictionalJSON, passphrase)` → `{envelopeJSON, recoveryKey}`。第3段階の架空JSONパッケージだけを入力にする。
- `validateEnvelope(envelopeJSON)` → 読み取り専用の正規化済み構造。構造・サイズ・対象の検証であり、暗号学的な完全性確認ではない。
- `decryptWithPassphrase(envelopeJSON, passphrase)` → 認証とレコード検証が成功した場合だけ、完全な元レコードを返す。
- `decryptWithRecoveryKey(envelopeJSON, recoveryKey)` → 同上。パスフレーズは不要。

架空データという指定は実データではないことの証明ではない。呼び出し元は既存データ取得処理を接続してはならない。
UI、ストレージ取得関数、保存先、イベント経由の実データ、外部通信は追加しない。

## 固定パラメータ

- format: `flower-journey-fictional-roster-vault`、version: `1`、source: `fictional-json`
- データ鍵（DEK）: 暗号化呼び出しごとに新しい AES-GCM 256ビット鍵を Web Crypto で生成。
- パスフレーズ鍵（KEK）: PBKDF2 / HMAC-SHA-256 / 600,000回 / 16バイト乱数salt → AES-GCM 256ビット。
- パスフレーズ: 最低16 Unicodeコードポイント、最大1024 UTF-16コード単位。空白だけを拒否し、入力を勝手にtrim・正規化せず、不正な単独サロゲートを拒否する。文字数は強度の保証ではない。1234は拒否する。
- 復旧鍵: `crypto.getRandomValues` による独立した32バイトのAES鍵。`FJREC1-`＋パディングなしBase64urlで返す。
- AES-GCM: IV 12バイト、タグ128ビット。データ・両鍵ラップ・全体認証で4つの異なるIVを使用。
- saltは同一サービスインスタンス内で再使用しない。乱数衝突時は再生成し、16回失敗で停止。
- 鍵・IVの利用は本APIの新規生成だけ。IVの持込み、同じDEKでの再暗号化API、既存暗号文の更新APIは公開しない。
- 平文最大2MiB、架空入力パッケージと暗号化JSONは最大4Mi UTF-16コード単位。実写真の大容量処理やチャンク化は未対応。

暗号文のJSONにはKDF条件、公開salt、IV、暗号化されたDEK、暗号文、認証タグを含める。
パスフレーズ・平文DEK・復旧鍵は含めない。復旧鍵は呼び出し元に別に返し、本モジュールは保存・ログ出力しない。戻り値全体をそのままJSON保存してはならず、将来も保存対象はenvelopeJSONだけとし、復旧鍵の保管は別手順で設計する。

## ラップと認証の関係

1. DEKをパスフレーズ由来KEKで `wrapKey('raw', ..., AES-GCM)`。
2. 同じDEKを独立した復旧鍵でもラップ。
3. DEKで名簿をAES-GCM暗号化。
4. 同じDEKと別IVで空メッセージをAES-GCM認証し、全体認証タグ（`auth`）を生成。

共通AADは、形式・バージョン・source・クラスID・年度・基準年度・既存キー・暗号方式と、用途文字列を含むUTF-8 JSON。
順序はモジュールの `metadata()` と `aad()` が固定する。受信JSONは既知フィールド順に再構築してから検証する。

- `roster`: 共通AADのみ。パスフレーズ用ラップに依存させない。
- `passphrase-dek`: 共通AAD＋KDF条件。
- `recovery-dek`: 共通AADのみ。
- `manifest`: 共通AAD＋KDF条件＋両ラップのIV/暗号文＋名簿のIV/暗号文。

使用しなかった鍵ラップへの改ざんも、全体認証で検出する。復号ではDEKを解除した後、全体認証→名簿認証・復号→既存形式の検証の順に進む。
実行中の復号用DEKは非抽出・decrypt専用。初回のラップ作成時だけDEKを抽出可能として生成し、平文DEKをAPIの戻り値へ出さない。

## 原本保護と失敗時

元JSONは読み取りのみ。入力配列や既存レコードを書き換えず、既存の検証・複製処理でID・正式名・顔写真・未知項目を保持する。
すべて完成して構造検証が終わるまで暗号化結果を返さず、途中失敗時は部分パッケージや復旧鍵を返さない。元JSONから再試行できる。
一時的な平文バイト列・復旧鍵バイト列は可能な範囲で上書きするが、JS文字列、CryptoKey、GC、OSメモリの完全消去は保証しない。

## 今後の課題

- Safari・Windowsブラウザの実機、PBKDF2待ち時間、バックグラウンド失効・復帰、容量・メモリ上限の評価。
- 鍵ラップの更新とパスフレーズ変更APIは未実装。形式上はラップと全体タグを更新すれば名簿本体の再暗号化を避けられるが、同じDEKを再使用する更新処理では、全履歴を含めたIV管理とクラッシュ時の整合性設計が必要。
- 保存トランザクション、世代管理、復旧鍵の別保管・再発行・保管確認、バックアップ復元テストは別段階。
- 以前のパスフレーズと古い暗号化コピーは、パスフレーズ変更だけでは失効できない。AES-GCMは、正しく認証された古い版への巻き戻しを単独では検出しない。
- この暗号化は解錠中の不正スクリプト・端末侵害・既存平文データを保護しない。暗号設計・実装の独立したレビュー前に実データへ適用しない。
