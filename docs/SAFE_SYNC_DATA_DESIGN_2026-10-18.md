# おもいでブック — 既存保存形式の調査と安全な同期設計（第1版）

作成日：2026-10-18  
対象：開発ブランチ `prototype-multiselect-lock-20261017` の `index.html`  
状態：**設計のみ**。実際の園児写真・園児情報・保存済みアルバムの同期は未実装。

## 1. 確認できた既存の保存先

| 種類 | 保存先 | 確認できた形 | 同期時の考慮 |
|---|---|---|---|
| 編集中・保存済みの見開き下書き | IndexedDB `omoide-rebuild-db-v1` / `drafts`（keyPath `id`） | `id`, `classId`, `year`, `title`, `background`, `caption`, `layout`, `photoGap`, `spreadIndex`, `designElements`, `photos`, `photoAssignments`, `thumbnail`, `updatedAt` | 既存の `putDraft` は同IDを上書きする。自動同期でそのまま呼ばない。 |
| 元となる編集写真 | 上記下書きの `photos[]` に内包 | `{name,type,blob}`。保存時に実際に読み込めるBlobを作り直す処理がある | 数MB以上も想定されるバイナリをメタデータから分離し、画像ハッシュで識別。元画質を維持。 |
| 写真の表示位置・文字・装飾 | 下書きの `designElements` 等 | ページ単位の複数要素 | 要素の参照先写真を壊さずコピー。キーと配列順の互換性を維持。 |
| ページ並び順 | localStorageの `omoide-project-slots-v1-<classId>` + 年度サフィックス | 各見開きスロットに下書きIDが入る | 下書きの本体とは**別**。同期時は両者の参照整合性が必要。 |
| クラス設定と園児名簿 | localStorageの `omoide-class-settings-v1` と `omoide-class-children-v1-<classId>`（年度別） | JSON文字列 | 個人情報を含むため、本物の同期API開放前にアクセス・保存先・解除を再設計する。 |
| 年度管理 | localStorageの `omoide-year-meta-v1` | 年度切替用メタ情報 | 「現在開いている年度」は端末ごとのUI状態として扱い、他端末の表示を不用意に変えない。 |
| 表紙（クラスごとの共通内容） | localStorageの `omoide-cover-v2-year-...` | タイトル等 | 専用オブジェクトとして分類。 |
| 成長記録と裏表紙写真等 | IndexedDB `omoide-special-cover-v1` / `covers` | 成長記録に顔写真Blob、裏表紙にも写真と設定を保存 | 下書きDBだけを同期しても引き継げない。別の資料・写真ストアが必要。 |
| 追加背景画像 | IndexedDB `omoide-my-backgrounds-v1` / `backgrounds` | 利用者追加の背景データ | 写真に準じた素材として扱い、権利・サイズ・ハッシュを確認。 |
| 端末引き継ぎ | `transferExportData` | `omoide-`で始まるlocalStorageキー＋下書きDBのみをJSONに変換 | **特別な表紙DBや追加背景DBは、この機能で完全にはカバーされない**。完全バックアップと呼ばない。 |

上記はソースコードの静的調査結果。実端末に保存された個別データは読み取っていない。

## 2. 同期のデータ構造（提案）

**同期メタデータ**と**元写真のバイナリ**を分ける。

```text
albumId / classId / schoolYear
  ├─ revision / baseRevision / lastSyncedRevision
  ├─ spreads[]                ページ順・下書きID・編集メタデータ
  ├─ assetManifest[]          画像参照・SHA-256・サイズ・MIME
  ├─ coverRecords[]           表紙・裏表紙・成長記録（段階的に対応）
  └─ rosterVersion            名簿の変更を別に管理

assets/<sha256>               画像のバイト列（複数ページで重複保存しない）
```

- **安定ID**：既存の `draft.id` と年度・クラスの組み合わせを保持する。同名アルバムでも別IDとして扱う。
- **写真参照**：現状の写真配列インデックスと `designElements` の参照関係を調べたうえで、既存の編集画面へ復元する互換レイヤーを作る。
- **完全性**：写真ごとに元のバイト列のSHA-256を計算して転送前後で照合。MIME・サイズ上限・受信の境界を検査する。サムネイルは派生データであり、原本として扱わない。
- **アップロードの順序**：必要な写真を仮領域へ保存・検証→メタデータの整合確認→新リビジョンを公開。途中失敗した場合は古い版を維持。
- **削除**：最初の同期バージョンでは端末間の自動削除をしない。後でゴミ箱・復元可能期限・確認・削除ログを導入する。
- **IDの衝突**：同IDで異なる内容なら自動上書きしない。利用者による比較・別コピー保存を提供する。
- **再接続**：送信進捗は再起動をまたいで再開できるよう、写真ごとの受領状況を永続化する。通信復帰の再試行は段階的に対応し、iOS Safariのバックグラウンド制限は別問題として扱う。

## 3. 保存を守るための順序

1. **読むだけのメタデータ検証（次の実装候補）**：下書きの件数・ID・年度・写真枚数・容量をユーザーの端末内で集計。写真や園児名をネット送信しない。
2. **本番とは別のダミー保存領域**：実際の `drafts` DBに書かず、架空アルバムを複数・画像付きで復元できるかテストする。
3. **読み取り専用のプレビュー同期**：実データを使うのはセキュリティ監査とバックアップ検証後。初期は受信を別コピーとして開くだけで、既存の下書きを上書きしない。
4. **衝突検出と比較**：アルバム、クラス、ページ並び、表紙を分けて改訂管理。サーバーのリビジョンが変わっていれば409で保存を拒否し、編集コピーを退避。
5. **ローカルネットワーク環境の検証**：macOS・iOS・WindowsでTLS、端末認証、復旧方法、オフライン編集、保存場所、容量制限、鍵・権限・端末紛失時の解除を検証する。
6. **明示的なオプトイン**：写真・クラス名簿など機微情報を同期する機能は、保存先・通信範囲・バックアップ・解除方法とともに案内し、本人の操作で有効化する。

## 4. 現在の制約・危険ポイント

- 現状の `putDraft` はID一致時に上書きするため、サーバーから読み込んだデータをそのまま保存すると端末側の編集を消すおそれがある。
- 下書きには写真Blobが内包されるため、JSONだけの差分比較や自動マージは安全でない。
- ページ順はlocalStorageにあるので、下書きだけ受け取ってもページ一覧の状態が揃うとは限らない。
- 成長記録・裏表紙・ユーザー追加背景は別IndexedDB。単一ストア同期だけでは不完全。
- 現行の接続テストはHTTPSとCookieによるプロトタイプ。**実際の園児データを送ってよい水準の認証・転送・監査が整ったとはまだ言えない**。
- すでにできている本体の編集・保存・写真読込機能には、この設計段階では変更を加えない。

## 5. 次に着手する最小実装

「設定 → 同期状況」に **端末内保存データの読み取り専用チェック** を追加する。集計対象は `getAllDrafts()` と必要なlocalStorageキーで、結果はその端末の画面にのみ表示する。写真Blobの中身や氏名・タイトルの表示は避け、サーバーへの送信もしない。エラー時にも既存データを消去・修復・上書きしない。

このチェックが成功したら、ダミーDB上で互換性のある写真参照の復元を段階的に検証する。

## 6. 手動の1アルバム別コピー引き継ぎ（実装：2026-10-18）

「設定 → 🔄 同期状況」の「📦 アルバムを別コピーで引き継ぐ（試験版）」を追加。

- **書き出し**: 端末内IndexedDBの下書きを1件だけ選択し、既存の `encodeBackup` によりBlob込みの専用JSON（`omoide-safe-single-album-copy` version 1）に変換する。書き出し元の下書き・写真は更新しない。
- **手渡し**: iPhoneからAirDropまたは「ファイルに保存」でMacBookに移す。HTTPS同期サーバー・GitHub・クラウドへ写真は送信しない。専用ファイルには写真・文字・配置など実内容が含まれるので取り扱い注意。
- **読み込み**: ファイル容量200MB以内、固定のフォーマット・バージョン・クラスID・年度・写真数・基本配列とBlobの有無を検査し、確認画面のあと**新しいランダムID**で `IndexedDB.add` を使って追加する。同じIDを上書きする `putDraft` は使わない。
- **閲覧**: 読み込まれたコピーは対象年度・クラスのプロジェクト一覧で見つかる設計。写真を実際に開けるかとページ配置が正常かは実機テストが必要。
- **制限**: 表紙・裏表紙・成長記録・追加背景・クラス名簿・ページの完全な並び順は移さない。この機能は全アルバムの自動同期・完全バックアップではない。ファイルの機密管理、失敗時の再試行と保存領域不足に注意。
- **安全性**: 同期サーバー用の認証・転送APIは呼ばない。既存データを削除しない。悪意ある改変ファイル対策と完全なデータ整合性検証はまだ製品レベルではないため、信頼できる自身のファイルのみ読み込む。

初回実機確認：iPhone上の下書き1件・写真12枚をエクスポート → AirDrop → MacBookの `localhost:3000` で新IDとしてインポート → クラス一覧から表示・写真12枚を確認。問題がある場合、iPhone側の元データは触らない。

## 7. 架空アルバムで未送信編集の復元テスト（2026-10-18）

`sync-server/fictional-album.html` に、ブラウザ内localStorageを使う**架空の選択肢3項目だけ**の下書き一時保存を追加した。

- 編集すると `baseRevision` と固定選択肢のタイトル・メッセージ・背景色を各端末内に保存する。サーバーには未送信。
- オンライン状態でページを再読み込みすると、選択肢とサーバー最新版を取得した後で、一時保存していた変更を復元する。
- 元のリビジョンとサーバー最新版が違うときは、既存の競合比較UIへ進める。保存成功または利用者が最新版を明示的に採用したら一時保存を消す。
- 通信が切れている間、画面上で編集内容を保持する。**サーバーが完全にオフラインの状態でページを新規表示・再読み込みすると、初期化の選択肢APIが利用できないため画面で編集を再開できるわけではない**。接続回復後に再読み込みして復元する想定。
- これは複数PC向け同期の**基礎挙動**のテストにすぎない。アプリ本体の下書きや実際の写真にはまだ適用していない。

実機テスト案：MacBookの架空アルバムでタイトル変更（保存ボタンは押さない）→Safari更新→「端末内の未送信編集を復元」が表示される→保存→iPhoneに反映される。次にiPhoneで変更・保存後、MacBookで未送信編集を保ったまま再読み込み→競合比較が表示されることを確認。

## 8. 接続先IP変更時の架空データ手動引き継ぎ（2026-10-18）

`sync-server/fictional-album.html` に「🔁 IPアドレス変更時の編集引き継ぎ」を追加。

- 元の画面から `version=1`, `baseRevision`, 固定選択肢 `title/message/color` **のみ**をJSONコードとして生成・コピー。写真・園児名・認証トークンは含まれない。
- 新しいアドレスの同ページにコードを貼り付けると、キーと値を検証してサーバー最新版を取得する。サーバーと内容が一致すれば何もしない。元リビジョンが違えば既存の競合UIで比較してから保存する。自動送信・自動上書きなし。
- 元の接続先の画面が**新しい更新版を読み込んでいない場合はこのボタンがない**。古い画面の内容を自動で救済できるわけではない。
- IPの自動発見、証明書再発行、再ペアリングを解消したわけではない。NAS導入に合わせ安定したホスト名や予約IP等が別途必要。
- テスト手順: Safariの `https://192.168.0.10:4318/fictional-album` と `https://localhost:4318/fictional-album` を両方ペアリング済みにし、前者で架空タイトルを未保存変更→コードをコピー→後者で貼り付け・復元→保存→前者のサーバー表示を確認。両ブラウザのオリジンは異なり、localStorageは独立している。
